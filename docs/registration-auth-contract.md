# 注册与登录适配契约（前端阶段）

2026-10-22：当前为 Next.js 静态导出，没有可运行的认证 POST API、数据库、验证码发件服务、人机供应商、短信绑定或实名供应商。以下是可信服务接入时必须实现的契约，不代表这些 HTTP 端点已存在。前端与 Mock 共享 `src/lib/auth/policy.ts`，正式服务应共享/复刻并版本化相同规则。

## 地区与渠道

`mainland` = 中国大陆（+86）；注册需要手机号资料，普通登录可使用已验证绑定的手机号或邮箱；微信未接入。`international` = 中国大陆以外，只允许邮箱注册与邮箱密码/验证码登录。用户明确选择地区，语言、邮箱后缀和精确定位不参与判断。声明的地区策略不是可信网络地理限制；若将来按网络所在地强制限制，须另设服务端判定及纠错流程。

服务端必须检查 region 枚举、purpose、channel、验证状态与角色，不能信任前端是否显示按钮。管理员沿用独立验证，不能把普通密码交给管理员通道获得身份。

## 人机和验证码

1. 人机供应商交互获取短期 token，绑定用途/地区/渠道/目标；供应商需先核实目标服务地区可用性。本阶段只有明确标记的开发模拟，不选定供应商或承诺可用性。
2. `send({ purpose, region, channel, recipient, humanToken })`：可信服务验证一次人机令牌（含提供商要求的域名、action、过期等），实施目标/IP/设备等限流，再生成 challenge。注册只支持邮箱；bind-phone 当前没有实现。
3. challenge 服务端记录 ID、用途、目标、创建与过期时间、尝试次数、消费状态；浏览器仅得到必要元信息，不得到真实验证码。验证码不进日志。
4. 本地 Mock 6 位测试码 `004271`，5 分钟有效、60 秒重发、最多 5 次失败；每次重发必须取得新的人机凭据。新 challenge 替换同渠道/目标的旧 challenge，跨用途切换也不能绕过目标频率限制。测试数字只在 Mock UI/测试夹具中显示，生产不发送也不显示。
5. 最终提交只消费对应 challenge + 字符串验证码；不会再次兑换已用的人机 token。用途、地区或目标不匹配一律拒绝；登录码不能注册，注册码不能登录。输入改变/离开会废弃当前 challenge。

## 注册

输入 `profile`：region、nickname（展示名，不唯一）、password、email、phone（仅大陆）、affiliation（individual/organization）、organization（仅组织必填）。前端没有 role 字段，Mock adapter 也明确拒绝传入 role；后端固定创建 USER。

此前没有注册密码策略。本轮为演示及待接入契约定义 12–128 字符、至少包含字母与非字母；不 trim、截断或改写密码；允许粘贴和密码管理器。正式密码策略需随真实身份服务核定，不能把客户端校验当作唯一安全措施。

发送验证码不提交/保存完整 profile 草稿。注册提交校验资料和对应邮箱 challenge 后原子创建账号；emailVerified=true、phoneVerified=false。电话格式正确仅代表可接受的待确认资料。个人记录明确为 individual，不要求公司名。已存在邮箱不能覆盖已有账号；错误保持通用。并发/超时重试使用 requestId 幂等与数据库唯一约束/事务，后端应绑定原始请求摘要并限制结果保留期。

本地 `accountService.register` 用 requestId + 不含密码/验证码的提交资料签名和 Promise 去重；内存 Map 插入前再次检查邮箱唯一性。已成功的相同请求可安全重试，不会创建第二个 ID。成功不操作 AuthProvider、不建立 session、不自动加购，只返回登录页的 `registered=1` 提示与经过 safeReturnTo 校验的目标。

本地新账号只允许虚构 `.test` 邮箱，资料和带盐 PBKDF2 校验值仅在当前 JS 内存，刷新、关闭或完整文档导航后失效。只有 Next 客户端站内导航保留该内存演示。原测试账号的稳定 ID/已验证绑定保留，原管理员数据源不新增账号。旧夹具明文已替换为带盐的 PBKDF2 校验值，不改变其测试密码。浏览器密码校验不提供正式身份信任。

## 登录与会话

密码登录检查现有账号记录与已验证标识，5 次失败后内存限制 5 分钟；正式服务必须实现跨实例的限流和风险策略，必要时要求人机验证。验证码登录先做人机验证，核验 login 用途的 challenge，再查找已存在 USER。两种方式是可选方式，不是双因素认证。没有账号时不会自动注册或自动跳转开户。

新账号未验证手机号不能登录、找回密码或合并账号。原明确预绑定的虚构手机号关系继续有效。未实现安全短信绑定，界面准确说明尚未接入。微信仍只显示未接入，不自动建立未绑定身份。

正式密码须由可信服务使用成熟密码哈希、TLS 和安全会话处理。生产会话应由可信认证系统管理（如安全 HttpOnly cookie），不能信任 localStorage 的角色。当前仅 Mock 存 `version/userId`，不存注册资料、密码、验证码或人机令牌；登录由共享 AuthProvider 提交后再导航。

## 返回和资料边界

注册 → 登录 → 购买/购物车/咨询之间使用现有 safeReturnTo 和 `/one-g` basePath。拒绝外部、登录/注册循环、角色不适用的路径；套餐、数量、支付偏好及 openContact/product 保留。不自动重复加购。密码、验证码、证件和 OAuth 密钥不进 URL。

实名入口默认折叠，只显示尚未开通，无证件输入，也不产生实名认证状态。未来必须单独确定用途、必要性、告知同意、合法核验流程、安全后端、最小存储、访问与删除规则，不能将人机/邮箱/格式校验视为实名。

未提交资料只在组件内存，不自动建草稿，不在 blur/visibilitychange 清空。用户确认离开清理表单和挑战；pagehide/pageshow（BFCache 恢复）清理旧内存。浏览器独立的密码管理器自动填充不由站点控制。验证码短期安全记录独立于草稿，“不保存草稿”不等于从未处理任何发送所需数据。请求若已被服务端提交，AbortController 不能回滚已发生的开户事务。
